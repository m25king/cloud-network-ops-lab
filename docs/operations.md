# 巡检、变更与回退手册

## 日常巡检

先检查用户业务，再检查设备和系统：HTTP业务与关键路径探测→告警→接口错误与利用率→邻居路由→CPU/内存/磁盘→备份任务与恢复抽检。空指标、采集失败、权限不足不能等同正常。

网络取证：display version、display interface brief、display ip interface brief、display ospf peer、display ip routing-table、display vrrp brief、display stp brief、display acl 3000、display current-configuration。CPU等命令按实际平台确认，不把不同厂商语法混用。

Linux取证：ip addr、ip route、ss -lntp、df -h、df -i、free -h、top、journalctl；容器查看docker compose ps和docker compose logs --since 10m。curl和DNS测试先区分IP连通性、域名解析、端口、TLS及应用返回。必要时在经授权的实验接口抓包，保留过滤条件。

## 具体示例：调整访客策略

实验中修改两核心ACL前保存原配置和正反测试。先在备用核心做预检查，记录新增规则号和精确规则内容；验证访客公网、内网隔离、DHCP以及管理访问，再按设计处理另一核心。不要用“先删掉整个ACL看看”作为常规恢复操作。若新增规则导致原本允许的业务失败，撤销新增规则并恢复原规则顺序，然后复测。

## 具体示例：更新应用镜像

先记录现版本和镜像ID，确认DB备份及基线。实验中的Compose没有编排滚动升级保障；逐个应用服务更新仍需持续观察Nginx请求结果和数据库就绪。失败时还原对应镜像版本并复测。数据库结构一旦变化，单纯回退应用镜像可能无效，需事先设计兼容迁移；本项目未做DDL在线变更。

## 故障复盘模板

业务影响→发现方式→时间线→已确认的证据→根因与排除项→恢复步骤→验证→预防改进。把“判断”“观测”“假设”分开。发现证据与原先假设冲突时修正假设，不删掉不符合结论的日志。

真实单位的变更审批、值班交接和安全要求以单位制度为准；本手册只用于个人实验的方法训练，不冒充企业流程。
