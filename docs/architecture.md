# 架构选择与风险边界

## 1. 网络层

采用传统园区二层接入、双三层核心与OSPF上联。5个VLAN对应办公、运维、服务器、访客、管理；两个MST实例将VLAN组分配给不同根桥，同步规划VRRP主用核心。该设计便于观察控制面状态和数据面路径。

AR2220需要同时面对双核心、分支、ISP；用WAN-SW和子接口承载两类逻辑链路，避免假设设备有不存在的第4个GE口。此实验交换机本身是单点，其作用是实验连线复用，不等同运营商传送网或双运营商专线。

两核心采用本地中转VLANIF，避免依赖部分模拟交换机不支持的三层物理口切换。相同中转VLAN编号不透传核心互联，因而处于不同广播域。

VRRP和MSTP只解决各自覆盖的失效。用户接口UP但两条路由上联全失、远端ISP黑洞、单DHCP服务停止、单分支上联停止和NAT状态丢失都可能影响业务。设计评估应列出失效域，而不是数设备数量后直接叫“高可用”。

## 2. 应用层

应用只实现进程健康、依赖就绪、模拟资产数量查询和指标端点。简单业务使运维问题容易定位。SQLite用于无需安装数据库的单机逻辑验证；Compose明确使用MySQL，不能混用两种证据。

Nginx通过被动重试容忍一个应用实例停止；Blackbox从代理入口探测就绪状态；Prometheus还单独抓取每个应用。二者组合覆盖“业务入口失败但应用实例正常”和“应用活着但数据库失效”。

所有组件在同一Docker宿主机、同一bridge网络，没有网络安全组隔离、TLS终止、双机数据库或负载均衡器冗余。因此定位为本地容器运维实验，而非完整私有云或多租户云平台。

## 3. 自动化层

输入限定为CSV/JSON清单，避免把巡检写成不受控网络扫描。HTTP只判断预期状态，TCP只检测握手；输出原始样本，保留失败原因，限制并发和请求次数。三次失败样本不能外推长期网络质量。

SSH适配器按显式列表只读采集。认证和主机密钥错误需要被用户处理，脚本不会绕过。接口解析是针对已支持格式的规则；格式未知返回unknown_format，比默认把空结果算正常更可靠。

## 4. 后续扩展优先级

1. 完成现有实验的真实验收，记录命令不兼容和修订。
2. 上联可达性检测联动、DHCP冗余和双上联分支：分别明确故障判据、回退和验证。
3. 容器按角色划分网络、数据备份加密和离机存储、跨主机服务部署。
4. 基于脱敏历史事件建立告警去重、时间关联和根因候选排序；先比较人工规则基线，再考虑模型。

这些均为计划，未作为当前实现能力。
